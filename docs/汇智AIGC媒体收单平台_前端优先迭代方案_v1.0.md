# 汇智AIGC媒体收单平台前端优先迭代方案 v1.0

版本：v1.0  
日期：2026-06-25  
适用范围：接单端、发布端报价撮合页、平台运营端轻审核页  
实施原则：**前端体验优先、业务逻辑优先、Mock 优先、接口预留、弱依赖本地后端**

---

## 1. 文档目标

本文不是数据库改造方案，也不是后端生产化方案，而是给后续开发 Agent 的统一施工标准。

目标：

1. 把当前“能跑但粗糙”的撮合流程，升级为可演示、可评审、可继续细化的产品化前端。
2. 统一前端信息架构、交互标准、页面完成度、组件复用方式。
3. 明确哪些必须做真逻辑，哪些只做接口契约与 Mock。
4. 避免开发过程中被本地调试后端牵着走，导致线上真实接入时前端重写。

---

## 2. 核心判断

当前项目的粗糙感，不是因为缺少订单、报价、结算规则，而是因为：

1. **有交易规则，没有交易产品感**  
   页面像管理后台，不像撮合平台。
2. **有状态，没有信任体系**  
   品牌方只能看价格，不能看“为什么选这个接单方”。
3. **有表单，没有标准化报价产品**  
   报价动作仍像填写字段，不像提交方案。
4. **有流程，没有经营漏斗**  
   接单方只能“看任务/看报价/看订单”，但没有连续经营视角。
5. **过早依赖本地后端形态**  
   容易把 Demo 接口当成真实契约，后续线上接入成本反而变高。

因此本轮迭代的方向不是继续横向堆功能，而是：

**把现有规则包装成成熟、可信、顺滑、可运营的前端产品。**

---

## 3. 总体实施原则

### 3.1 优先级原则

必须遵守以下优先级：

1. 用户体验
2. 前端业务逻辑完整性
3. 组件抽象与页面一致性
4. Mock 数据完整度
5. 接口契约清晰度
6. 本地后端联通性
7. 本地数据库真实性

结论：

- 本地数据库不是本轮验收重点。
- 后端只需要支持演示、联调、状态说明，不需要过度生产化。
- 如果后端数据不稳定，允许前端直接切 Mock，只要交互和状态机不变。

### 3.2 Mock-first 原则

所有新页面、新卡片、新流程必须先满足：

1. 无真实接口时可完整演示。
2. 刷新页面后能稳定回到合理状态。
3. 切换不同任务状态时 UI 不崩。
4. 空态、加载态、错误态、长文案态都完整。

推荐实现方式：

1. 建立页面级 ViewModel Mock。
2. 建立统一的类型定义与 mapper。
3. 真实接口只负责把服务端响应转换成前端 ViewModel。
4. 禁止页面直接依赖后端原始字段散落渲染。

### 3.3 接口弱绑定原则

接口只做三件事：

1. 提供页面所需数据契约
2. 提供用户操作事件入口
3. 返回状态变化结果

禁止：

1. 让前端页面结构贴死当前 Prisma 表结构
2. 在组件内部直接理解数据库字段含义
3. 用“后端还没返回这个字段”为理由降低页面完成度

推荐：

1. 页面先定义前端 DTO / ViewModel
2. API 层做 adapter
3. Mock 和真实 API 共用同一份 ViewModel

## 4. 本轮产品目标

本轮只聚焦三段核心体验：

1. **接单方发现任务并提交标准化报价**
2. **发布方比较多个报价并做决策**
3. **平台运营能轻量判断供给质量与履约可靠性**

一句话目标：

**把“报价撮合”做成一个可信、可比较、可决策、可交付的前端产品闭环。**

---

## 5. 迭代范围

## 5.1 P0 必做范围

### 接单端

1. 首页重构为经营工作台
2. 任务大厅重构为“筛选 + 推荐 + 决策说明”
3. 任务详情重构为“任务要求 + 品牌简报 + 报价入口”
4. 提交报价页重构为标准报价卡
5. 我的报价页重构为报价漏斗列表
6. 我的订单页提升信息密度与履约视图
7. 个人主页补齐可信度展示

### 发布端

1. 比价页重构为“服务商决策页”
2. 发单页强化建议区间、隐藏预算和解释性提示
3. 发单管理中强化报价进度和下一步动作

### 平台端

1. 开放轻量版“供给审核视图”
2. 开放轻量版“履约评分视图”
3. 仅做前端视图、Mock 数据与操作说明，不强依赖真实审核后端

## 5.2 P1 建议范围

1. 匹配解释系统
2. 轻量案例审核
3. 报价模板和历史复用
4. 复投推荐
5. 平台侧供给分层

## 5.3 本轮不做

1. 真实支付
2. 真实分账
3. 真实提现风控
4. 线上数据库设计定稿
5. 重后端审核流
6. 复杂即时聊天
7. 大规模运营后台重构

## 6. 页面级改造方案

## 6.1 接单端首页

当前问题：

1. 首页更像静态概览，缺乏经营动作入口
2. 推荐任务只展示 3 条，信息价值不足
3. “报价”“订单”“收益”彼此割裂

改造目标：

把首页改为“接单经营工作台”，核心围绕今日可做什么。

模块结构：

1. 顶部经营摘要
   - 待报价
   - 已报价待确认
   - 履约中
   - 待验收
   - 可结算金额
2. 今日优先事项
   - 报价即将过期
   - 返修待处理
   - 待补交付证明
3. 推荐任务
   - 不只展示结果，还展示推荐原因
4. 最新报价动态
5. 履约表现卡

交互要求：

1. 每张卡必须可点击进入具体列表
2. 每张卡必须有明确状态解释
3. 不允许只有数字没有动作出口

## 6.2 任务大厅

当前问题：

1. 只有基础筛选，没有平台化推荐感
2. 匹配度只有百分比，没有解释
3. 品牌方视角和接单方视角之间的信息翻译不够

改造目标：

让任务大厅从“任务列表”升级为“可判断是否值得报价的任务市场”。

必须新增：

1. 筛选区
   - 平台
   - 行业
   - 内容方向
   - 截止时间
   - 报价任务 / 固定预算任务
2. 排序区
   - 推荐优先
   - 最新发布
   - 最早截止
   - 高匹配优先
3. 任务卡字段
   - 标题
   - 品牌名
   - 平台
   - 内容方向
   - 建议报价区间
   - 匹配度
   - 匹配原因
   - 截止时间
   - 当前状态
4. 任务详情抽屉或详情页
   - 任务背景
   - 品牌简报
   - 交付物
   - 验收标准
   - 可提供证明
   - 常见问题

匹配说明文案标准：

不要只写“高度匹配”，必须拆出具体理由，例如：

- 平台吻合：你已声明可做小红书
- 行业接近：你近 30 天有医美/教育类报价记录
- 内容方向匹配：你擅长测评/种草稿

## 6.3 报价提交页

当前问题：

1. 表单字段太少
2. 缺少结构化服务承诺
3. 已有建议区间和 over-range 规则，但前端承接不完整

改造目标：

把“提交报价”做成标准化报价方案。

页面结构：

1. 任务摘要区
2. 建议区间区
3. 报价输入区
4. 履约承诺区
5. 交付证明区
6. 补充说明区
7. 成交金额自动计算区

必须字段：

1. 期望到手价 P0
2. 媒体名称 / 账号定位
3. 预计上线时间
4. 是否含链接
5. 是否含截图
6. 是否含收录证明
7. 交付承诺
8. 报价说明

超建议区间规则：

1. 超出建议区间时必须展示强提醒
2. 自动展开“原因说明”
3. 未填写原因不可提交

成交金额展示标准：

必须同时展示：

1. 你预计到手金额
2. 平台技术服务费
3. 发布方成交支付价

但注意：

- 接单方页可以展示 P0/F/G
- 发布方页只能展示 G，不展示 P/F

## 6.4 我的报价

当前问题：

1. 列表过于简陋
2. 看不到报价生命周期
3. 无法体现“经营感”

改造目标：

把“我的报价”改成报价漏斗视图。

列表分组：

1. 待确认
2. 已中标
3. 未中标
4. 已过期
5. 已转订单

每条报价展示：

1. 品牌
2. 任务标题
3. 报价时间
4. 到手价 P0
5. 成交价 G
6. 报价有效期
7. 当前状态
8. 下一步建议动作

可以增加的增强项：

1. 是否在建议区间内
2. 与最低报价差距
3. 报价被确认概率标签

## 6.5 我的订单

目标：

让订单页更像履约中台，而不是简单记录列表。

新增模块：

1. 订单阶段时间轴
2. 待补交付项提示
3. 验收意见摘要
4. 返修版本管理
5. 结算进度说明

文章类任务必须区分：

1. 草稿提交
2. 审稿中
3. 待终稿发布
4. 最终验收

非文章类任务必须区分：

1. 待开始
2. 履约中
3. 已提交证明
4. 待验收
5. 已完成

## 6.6 接单方个人主页

目标：

把个人主页从“资料页”提升为“接单方名片”。

必须展示：

1. 基础身份信息
2. 实名认证状态
3. 提现账户状态
4. 可接平台
5. 服务地区
6. 行业偏好
7. 案例链接
8. 报价区间
9. 报价说明
10. 轻量履约表现

新增可信度标签：

1. 已实名认证
2. 已绑定收款账户
3. 平台能力已声明
4. 有历史成交
5. 有案例展示

## 6.7 发布端比价页

这是本轮最重要的页面之一。

目标：

把“比价格”升级为“比方案、比稳定性、比交付能力”。

表格列建议：

1. 接单方
2. 认证状态
3. 可发媒体
4. 成交价 G
5. 最早上线
6. 交付证明
7. 履约表现
8. 报价说明
9. 推荐标签
10. 选择动作

必须支持：

1. 单选报价
2. 查看接单方详情
3. 查看案例
4. 查看履约记录摘要
5. 确认后冻结提示

确认区文案标准：

1. 只展示发布方实际支付 G
2. 明确“确认后才冻结”
3. 明确“确认后进入执行阶段”

禁止：

1. 展示平台费 F
2. 展示接单方到手价 P0
3. 让页面像财务分账页

## 6.8 发布端发单页

目标：

让品牌方知道自己在“发布一个可成交任务”，而不是填写复杂表单。

必须强化的感知：

1. 为什么建议这个区间
2. 为什么拆成这些任务
3. 每条任务的最高可接受价
4. 报价阶段不冻结
5. 确认报价后才冻结

建议新增：

1. 任务预览卡
2. 可成交性提示
3. 推荐供给画像说明

## 6.9 平台端轻审核页

目标：

即使本期不做完整后台，也要让平台端具备“可运营感”。

轻审核页包含：

1. 接单方能力声明列表
2. 案例完整度
3. 实名与收款绑定状态
4. 历史报价数
5. 中标率
6. 履约完成率

这里只做：

1. 前端视图
2. 状态标签
3. Mock 审核动作
4. 操作留痕提示

不要求：

1. 接真实审核流
2. 接真实财务系统

## 7. 数据与接口策略

## 7.1 前端 ViewModel 必须先行

每个页面都必须先定义前端所需 ViewModel。

例如报价卡不应直接依赖数据库对象，而应抽象为：

1. `TaskMarketplaceCardViewModel`
2. `QuoteSubmissionViewModel`
3. `QuoteCompareRowViewModel`
4. `ProviderTrustProfileViewModel`
5. `ProviderOrderTimelineViewModel`

要求：

1. ViewModel 字段名面向 UI 语义
2. 页面只消费 ViewModel
3. API response 必须经过 adapter
4. Mock data 必须直接产出 ViewModel

## 7.2 Mock 数据标准

每个页面至少准备以下数据集：

1. 空态
2. 少量数据态
3. 高密度列表态
4. 长文案态
5. 异常态
6. 权限受限态
7. 已过期/已完成等边缘状态

Mock 数据要求：

1. 命名真实
2. 不要全是“测试任务 1/2/3”
3. 品牌名、行业、平台、交付要求要像真实业务
4. 同一流程上下游数据要能对得上

## 7.3 接口设计要求

后端只需提供契约，不要求本轮深度实现。

接口必须满足：

1. 路径明确
2. 输入输出稳定
3. 字段注释清晰
4. 状态枚举固定
5. 错误码可读

建议对每个接口补三样：

1. request example
2. response example
3. mock fallback 说明

## 8. 前端开发规范

以下规范是本轮开发的硬约束。

## 8.1 组件原则

1. 先组合，后抽象
2. 同类卡片必须统一结构
3. 同类状态标签必须统一颜色、文案、尺寸
4. 不允许同一状态在不同页面有不同命名
5. 不允许把业务判断散落在 JSX 模板里

## 8.2 页面原则

1. 页面必须有空态、加载态、错误态
2. 页面必须有骨架屏或至少稳定占位
3. 不允许列表闪烁、跳高、布局抖动
4. 不允许操作按钮位置频繁变化
5. 不允许弹窗里再套复杂弹窗

## 8.3 信息密度原则

这是 B 端交易平台，不是营销页。

要求：

1. 首屏必须能扫到核心信息
2. 次级细节进入抽屉或详情
3. 不用大段说明文字替代结构化信息
4. 文案要短、准、可扫

## 8.4 表单原则

1. 所有必填项显式标记
2. 所有金额字段必须有单位
3. 所有日期字段必须明确时区或相对关系
4. 提交前必须本地校验
5. 提交后必须给出结果反馈
6. 错误提示写人话，不写技术报错

## 8.5 状态机原则

前端必须显式处理以下状态：

1. `quote_open`
2. `quote_review`
3. `awaiting_freeze`
4. `matched`
5. `in_progress`
6. `draft_review`
7. `revision`
8. `pending_review`
9. `completed`
10. `cancelled`
11. `disputed`

要求：

1. 每个状态有统一中文文案
2. 每个状态有统一标签样式
3. 每个状态有明确下一步动作
4. 页面不能出现“未知状态”裸值

## 8.6 视觉与布局原则

1. 延续当前仓库的平台端/接单端设计规范
2. 不做营销风大卡片
3. 不做大面积渐变
4. 不做夸张圆角
5. 不做悬浮感过重的装饰
6. 优先白底、浅灰底、弱边框、清晰分区

## 8.7 响应式原则

1. 桌面端优先
2. 1024px 以下必须可用
3. 移动端不要求完整后台体验，但不能错位
4. 表格在窄屏下必须可降级为卡片或横向滚动

## 8.8 可维护性原则

1. 页面类型、状态常量、映射文案统一放到 lib
2. 同类 mapper 放到独立 adapter
3. 复杂业务卡片拆独立组件
4. 不允许一个页面文件同时承担请求、状态机、渲染、格式化、文案映射全部职责

## 9. 建议的前端目录策略

建议后续 Agent 按以下方式组织：

1. `views/` 放页面
2. `components/` 放页面组件
3. `lib/` 放状态映射、formatter、adapter、常量
4. `mocks/` 放页面级 Mock 数据
5. `types/` 或局部 `types.ts` 放 ViewModel 类型

建议新增：

1. 接单端 `mocks/provider-marketplace.ts`
2. 接单端 `mocks/provider-quotes.ts`
3. 发布端 `mocks/quote-compare.ts`
4. 平台端 `mocks/provider-review.ts`

## 10. 验收标准

## 10.1 视觉验收

1. 所有核心页首屏结构清晰
2. 信息层级统一
3. 按钮、Tag、输入框尺寸统一
4. 无明显布局错位
5. 无大段空白和拥挤堆叠

## 10.2 交互验收

1. 任务大厅到报价页路径顺畅
2. 比价页到确认动作顺畅
3. 我的报价到我的订单跳转顺畅
4. 错误态和空态可演示
5. 关键操作都有反馈

## 10.3 业务验收

1. 接单方能理解该不该报价
2. 品牌方能理解该选谁
3. 平台运营能理解供给质量如何
4. 报价、确认、交付、验收四段流程感完整

## 10.4 Mock 验收

1. 断开真实接口后页面仍可演示
2. Mock 状态切换后页面表现合理
3. 不依赖本地数据库手工造数才能展示关键流程

## 12. 给后续开发 Agent 的执行要求

1. 先读本文，再动页面。
2. 先定义 ViewModel，再写接口调用。
3. 先用 Mock 把页面做完整，再接真实接口。
4. 不要因为本地后端字段不完整而降级页面设计。
5. 不要为了省事把数据库字段直接渲染到页面。
6. 不要新增与现有状态机冲突的自定义状态。
7. 不要让接单端、发布端、平台端各写一套状态文案。
8. 不要优先做后端生产化。
9. 不要跳过空态、错误态、超长文案态。
10. 每完成一页，至少自查一次“像不像一个成熟撮合平台”，而不是“能不能显示数据”。

## 13. 最终结论

本轮最重要的不是继续加模块，而是把已有撮合规则做成产品。

真正要交付给后续 Agent 的，不是“接个接口把数据渲出来”，而是：

1. 一个可信的接单市场
2. 一个标准化的报价产品
3. 一个可决策的比价界面
4. 一个可经营的接单工作台

只要这四件事做扎实，哪怕后端继续用 Mock，平台的完成度也会从“粗糙 Demo”明显提升到“可交付产品原型”。
