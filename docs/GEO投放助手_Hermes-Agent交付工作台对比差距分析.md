# GEO 投放助手 · Hermes Agent 交付工作台对比差距分析

生成日期：2026-06-05  
对比来源：用户提供的 ChatGPT 分享页《GEO撮合交易平台探讨》  
本地对照：当前项目代码、`README.md`、`docs/GEO投放助手_正式开发版_PRD_v1.1_最新设计风格.md`、`docs/Hermes-POC.md`、`docs/GEO投放助手_缺口Issue清单.md`

---

## 1. 结论

分享页的核心判断是：第一阶段不要把产品做成完整“GEO 撮合交易平台”，而应先收敛成 **GEO Agent 交付工作台**。

推荐的 MVP 闭环是：

```mermaid
flowchart LR
  A["品牌方输入一句 GEO 目标"] --> B["生成 GEO 任务包"]
  B --> C["本地 Hermes Agent 执行"]
  C --> D["人工确认高风险动作"]
  D --> E["留存链接 / 截图 / 日志 / AI 回答结果"]
  E --> F["生成客户可读 GEO 报告"]
  F --> G["复盘下一轮优化"]
```

当前项目已经具备发布端、接单端、平台端、订单、余额、AgentTask、GEO 报告、Hermes Gateway 适配等较多骨架，但产品重心仍偏“大而全投放/撮合平台”。与分享页建议相比，最需要补的是：

1. **本地 Hermes 执行器产品化不足**：现在有 Gateway 适配和账号校验页面，但还没有面向小白用户的安装器、就绪检查、权限说明、技能自动安装和安全确认台。
2. **GEO Skills 资产不足**：代码里有任务类型到 skillName 的映射，但没有真正沉淀可安装、可版本化、可验收的 6 个核心 GEO Skills。
3. **报告还不够像核心交付物**：已有 GEO 报告和 PDF，但报告数据仍偏 mock/摘要，缺少问题集、AI 回答原文、截图、引用来源、竞品出现、任务证据链和复测趋势。
4. **安全边界不够产品化**：有 `needsReview` / `reviewCategory`，但缺少白名单 skill、危险动作审批、凭证本地化、执行前预览、执行后留证的完整闭环。
5. **MVP 范围仍偏重**：接单端、平台端、结算、资源市场都在推进，但分享页建议第一阶段应先验证 3-5 个客户是否愿意为“AI 搜索可见度交付”付费。

## 2. 分享页建议的第一阶段范围

### 2.1 产品定位

不要一开始叫“撮合平台”。更准确的定位是：

> 让企业把一句 GEO 目标，变成可执行、可留证、可复盘的 AI 搜索优化任务。

产品主线不是“找人发稿”，而是：

1. 发布端生成 GEO 任务包。
2. 本地 Hermes Agent 通过 GEO Skills 执行诊断、内容优化、发布辅助、监测和留证。
3. 平台生成客户能看懂、愿意付费的 GEO 可见度报告。

### 2.2 第一阶段只做 3 个核心闭环

| 闭环 | 分享页建议 | 当前项目情况 | 差距 |
|---|---|---|---|
| 发布端任务包 | 用户输入目标，生成官网优化、问答内容、测评内容、FAQ、结构化信息等任务 | 已有生成文章、GEO 分析、发起订单、任务包草稿、内容库 | 任务包仍更像投放/发单，未突出“自有资产 GEO 优化任务包” |
| 本地执行器 | 用户安装客户端，看到自有品牌包装，不直接面对 Hermes 原生界面 | 有 `docs/Hermes-POC.md`、`NousHermesExecutor`、`/api/hermes/health`、发布账号校验 | 缺安装器、技能安装、权限引导、执行器状态页、失败诊断 |
| GEO 报告 | 交付链接、截图、内容变更、AI 回答结果、品牌/竞品出现情况 | 有 `GeoReport`、报告历史、PDF、水印、分享页 | 缺原始采样、截图证据、任务证据链、趋势复测和客户化解释 |

## 4. 主要没做好的地方

## P0：影响 MVP 是否成立

### P0-01 产品主线仍然过重，第一阶段焦点不够尖

**现状**

当前发布端导航包含工作台、品牌管理、GEO 分析、排名监控、内容库、发起订单、订单交付、运行日志、发布账号、账户余额等；接单端和平台端也已具备大量交易/运营功能。

**问题**

分享页建议第一阶段先验证“GEO Agent 交付工作台”，而不是直接验证完整撮合交易市场。现在项目容易把研发资源分散在接单、结算、改派、平台审核、资源市场等能力上，反而削弱最关键的客户价值：

> 客户是否认为这套流程能帮他理解并推进 GEO。

**建议**

第一阶段产品验收改为：

1. 一个品牌可以输入目标。
2. 系统生成 3-5 个自有资产 GEO 任务。
3. 本地执行器完成至少 2 类安全动作。
4. 产出可分享 PDF 报告。
5. 报告中包含证据链和下一步优化建议。

接单端和平台端保留骨架，但不要作为 MVP 成败的第一验收口径。

---

### P0-02 缺少“本地执行器客户端 / 安装器”产品层

**现状**

`docs/Hermes-POC.md` 面向开发者，要求用户执行安装脚本、配置 `hermes setup`、设置 API Server、启动 gateway。发布端也有 Hermes 在线状态和账号校验，但还不是普通客户能用的产品化流程。

**问题**

分享页特别强调：不要让小白直接面对 Hermes 原生配置。用户需要看到的是“GEO 本机执行器已就绪”，而不是 GitHub、CLI、gateway、API Key、权限命令。

**建议新增**

| 模块 | 功能 |
|---|---|
| GEO 本机执行器下载页 | 按 macOS / Windows 提供安装包或安装指引 |
| 首次启动向导 | 检测 Python / Node / Git / rg / browser 权限 / Hermes CLI / gateway |
| 平台账号绑定 | 扫码或一次性 token，将本机执行器绑定到 GEO 投放助手账号 |
| Skills 自动安装 | 自动安装和更新 GEO Skills |
| 就绪页 | 显示 Hermes 在线、技能版本、浏览器权限、最近心跳 |
| 诊断页 | 一键导出环境诊断，方便运营兜底 |

**建议新增文档**

`docs/GEO投放助手_本机执行器产品化方案.md`

### P0-03 缺少可版本化的 6 个核心 GEO Skills

**现状**

`server/lib/agent-skill.ts` 有以下映射：

| taskType | skillName |
|---|---|
| `article_generation` | `geo.article.generate` |
| `geo_analysis` | `geo.analysis.run` |
| `campaign_plan` | `geo.campaign.plan` |
| `website_preview` | `geo.website.preview` |
| `hermes_publish` | `hermes.publish.auto` |
| `account_verify` | `geo.account.verify` |
| `keyword_mining` | `geo.keyword.mine` |
| `index_sampling` | `geo.index.sample` |
| `article_rewrite` | `geo.article.rewrite` |

但这些更像任务名/路由名，还没有在仓库中形成真正可安装、可测试、可版本化的 Hermes/Agent Skills 包。

**分享页建议第一阶段只做 6 个核心 Skill**

1. 检查网站/页面 GEO 基础问题。
2. 生成 AI 提问场景和问题集。
3. 生成 FAQ / Schema / llms.txt。
4. 改写页面/文章，让内容更容易被 AI 引用。
5. 辅助发布和截图留证。
6. 定期测试 DeepSeek、豆包、Kimi、百度 AI 搜索、通义、元宝等回答并生成报告。

**建议**

在仓库新增 `skills/geo/` 或 `external-skills/geo/`，每个 skill 至少包含：

1. `SKILL.md`
2. 输入 JSON Schema
3. 输出 JSON Schema
4. 安全级别：read-only / suggest-only / needs-confirm / high-risk
5. 示例输入输出
6. 本地 smoke 测试
7. 版本号和 changelog

### P0-04 报告缺少“客户愿意付费”的证据链

**现状**

已有 `GeoReport` 表和报告历史页面，字段包括提及率、排名、内容缺口、竞品分析、优化建议，并支持 PDF 水印和分享。

**问题**

现在报告更像 AI 生成摘要。分享页里的 MVP 核心交付物应能回答客户最关心的问题：

1. 我在 AI 搜索里有没有被看见？
2. 哪些问题里出现了我？
3. 竞品是否出现？
4. AI 回答引用了哪些网页或内容？
5. 这轮优化做了什么？
6. 有哪些链接、截图、日志能证明？
7. 下一轮怎么提升？

**建议新增数据对象**

| 对象 | 作用 |
|---|---|
| `GeoQuestionSet` | 客户想覆盖的问题集 |
| `GeoAnswerSample` | 每个平台、每个问题的一次 AI 回答采样 |
| `GeoMention` | 品牌/竞品出现、位置、上下文 |
| `GeoCitation` | 引用来源、链接、片段 |
| `GeoEvidence` | 截图、HTML、日志、链接、内容变更记录 |
| `GeoReportRevision` | 报告复测版本和趋势 |

**报告页面建议**

从“摘要报告”升级为：

1. 执行概览。
2. 问题覆盖矩阵。
3. AI 回答采样。
4. 品牌与竞品出现情况。
5. 引用来源与证据截图。
6. 已完成优化动作。
7. 下轮任务包。

---

### P0-05 高风险动作确认和安全白名单不完整

**现状**

`AgentTask` 有 `needsReview` 和 `reviewCategory`，发布记录也能记录失败分类；账号绑定页有本机登录态校验；PRD 中也提到危险动作需要确认。

**问题**

分享页强调：可以建议、生成、填充、留证，但发布、删除、改代码、提交后台这类动作不能默认自动执行。当前项目还缺少统一的“执行前预览 + 用户确认 + 白名单 skill + 审计留证”产品层。

**建议新增**

| 能力 | 要求 |
|---|---|
| Skill 白名单 | 只允许执行平台配置过的 GEO Skills |
| 风险等级 | read-only / draft / fill-form / publish / destructive |
| 执行前预览 | 展示 Agent 准备访问的网站、将填写的内容、将点击的按钮 |
| 用户确认 | 高风险动作必须二次确认 |
| 凭证边界 | 平台不上传用户平台账号密码，敏感凭证留在本机 |
| 审计日志 | 记录谁确认、确认了什么、执行结果是什么 |
| 运营兜底 | 失败后可标记 `need_reauth` / `need_manual_publish` / `retry_ok` |

## P1：影响交付效率和复购

### P1-01 自有资产优化还不够突出

分享页建议早期少做外部媒体撮合，先从客户自有资产开始：

1. 官网。
2. FAQ。
3. Schema。
4. llms.txt。
5. 知乎/公众号/百家号等自有账号。
6. 内容库。

当前项目有创建网页、生成文章、发布账号、内容库，但“官网/页面 GEO 基础诊断”和“结构化信息生成”还不够明显。

建议新增一级或二级能力：**自有资产优化**。

可包含：

1. 页面 GEO 体检。
2. FAQ 生成。
3. Organization / Product / LocalBusiness Schema 生成。
4. llms.txt 生成。
5. 页面标题、摘要、实体一致性检查。
6. 修改建议和人工确认清单。

---

### P1-02 AI 平台监测仍偏 mock，缺少真实采样策略

当前 `DirectModelExecutor` 的 `index_sampling` 和 `geo_analysis` 仍是 mock 逻辑。分享页建议至少对 DeepSeek、豆包、Kimi、百度 AI 搜索、通义、元宝等做周期性测试。

建议先定义半自动采样标准：

| 项 | 建议 |
|---|---|
| 问题来源 | 品牌词、品类词、竞品词、购买决策词、本地场景词 |
| 平台范围 | 先 3 个：豆包、Kimi、百度 AI 搜索；再扩展 |
| 采样频率 | 手动触发 + 每周复测 |
| 留证 | 回答文本、截图、URL、时间、平台、账号环境 |
| 评分 | 品牌出现、竞品出现、是否引用、引用来源质量、回答语义位置 |

---

### P1-03 运营人工兜底流程还需要前置

分享页明确说早期一定会有很多 Agent 执行失败，必须允许运营人工兜底。

当前平台端已有 Agent 任务、订单、待办和失败分类，但还需要把“Agent 失败后如何变成运营可处理任务”做成标准流程：

1. 失败自动分类。
2. 运营接手任务。
3. 手动补充链接/截图/说明。
4. 报告中标注“人工复核/人工完成”。
5. 客户侧看到的是完整交付，不是技术错误。

---

### P1-04 任务命名和按钮语言仍有“派单平台”味道

分享页建议主按钮不要叫“发布任务”，更像 Agent 工作台的语言应是：

1. 生成 GEO 任务包。
2. 让 Agent 生成 3 个 GEO 任务。
3. 开始本机执行。
4. 生成可见度报告。
5. 复测 AI 可见度。

当前项目里还有“发起订单”“订单交付”“找人投放/接单端”等强交易语义。建议 MVP 路径中降低交易感，突出“诊断、执行、留证、报告”。

---

## P2：平台化前再补

### P2-01 完整撮合市场可以后置

接单端、结算、改派、平台审核、资源管理都已经有基础，但分享页建议等以下条件满足后再重点投入：

1. 至少 3-5 个付费试点客户。
2. 至少 20 个可控内容/媒体资源。
3. 有明确 GEO 内容模板和验收标准。
4. 有基础 AI 可见度报告。
5. 30-60 天试点跑通复购或复盘。

### P2-02 效果结算不要过早承诺

分享页提醒不要承诺：

1. 保证被 AI 推荐。
2. 保证 7 天进入 AI 答案。
3. 保证 ChatGPT 引用。

建议合同和页面统一表述为：

> 帮企业建设更容易被 AI 搜索理解、检索和引用的内容资产，并持续追踪品牌在 AI 问答中的可见度变化。

## 6. 建议排期

### 第 1 周：收敛 MVP 和报告骨架

1. 明确第一阶段只验收“Agent 交付工作台”。
2. 定义 6 个核心 GEO Skills。
3. 定义报告证据链数据结构。
4. 把“发起订单”路径中的 MVP 主按钮改为“生成 GEO 任务包”。

### 第 2 周：本机执行器产品化 POC

1. 新增本机执行器状态页。
2. 增加绑定 token 和心跳。
3. 增加技能版本检查。
4. 增加执行前确认面板。

### 第 3 周：报告证据链

1. 采样问题集。
2. AI 回答留存。
3. 截图/链接/日志证据。

## 7. 最小验收标准

第一阶段不要用“平台上线”验收，应改用以下业务闭环：

1. 用户能输入一句 GEO 目标，并生成结构化任务包。
2. 本机执行器能完成至少 2 类安全动作：页面诊断、FAQ/Schema/llms.txt 生成、内容改写、截图留证。
3. 高风险动作必须人工确认。
4. 每个任务有日志、状态、输出和证据。
5. GEO 报告能展示品牌出现、竞品出现、问题集、回答采样、引用/截图/链接证据。
6. 客户能基于报告理解“现在怎么样、做了什么、下一步做什么”。
7. 运营能在 Agent 失败时人工补全交付。

---

## 8. 一句话建议

当前项目基础不错，但下一步不要继续横向堆平台模块。应先把产品从“GEO 投放/撮合平台”校准为“GEO Agent 交付工作台”：先把本地执行器、安全确认、GEO Skills、证据链报告这四件事做深，再决定是否扩大接单端和资源市场。
