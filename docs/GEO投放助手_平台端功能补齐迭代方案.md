# GEO 投放助手平台端功能补齐迭代方案

版本：v1.2 平台端补齐方案  
日期：2026-06-04  
依据：当前代码检查，发布端与接单端已大幅改造，平台端需要升级为统一运营中台  
开发口径：以真实运营闭环为交付标准，不以 mock 展示作为完成标准

---

## 1. 检查结论

当前平台端已经不是完全空白，已具备运营看板、Agent 监控、Hermes/本地自动化记录、接单方审核、任务订单监管、网站订单、商家、资金、配置、审计等基础能力。但平台端仍集中在 `src/apps/platform/PlatformApp.tsx` 单文件内，信息架构、筛选能力、详情页深度和治理动作已经落后于发布端与接单端的新功能。

发布端当前主线已变为：

| 发布端能力 | 平台端应具备的监管视角 | 当前状态 |
|---|---|---|
| 工作台 | 全局运营待办、风险分级、异常处理入口 | 部分已有 |
| 品牌管理 | 商家/品牌档案、企业认证、禁用启用、品牌风险 | 部分已有 |
| GEO 分析 | Agent 任务、报告质量、算力消耗、失败重试 | 部分已有 |
| 排名监控 | 查询计划、周期任务、命中异常、结果审计 | 缺失 |
| 内容库 | 内容批次、内容状态、发布前审稿、违规风险 | 缺失 |
| 发起订单 | 任务订单、申请接单、派单、改派、验收 | 部分已有 |
| 订单交付 | 交付物审查、返修、争议、结算状态 | 部分已有 |
| 运行日志 | Agent 详情、Skill、本地自动化、人工接管 | 部分已有 |
| 发布账号 | 授权状态、登录风险、自动发布失败归因 | 缺失/分散 |
| 账户余额 | 入账、冻结、释放、AI 算力、异常流水 | 部分已有 |

接单端当前主线已变为：

| 接单端能力 | 平台端应具备的监管视角 | 当前状态 |
|---|---|---|
| 首页 | 接单方履约风险、待处理通知、收益状态 | 缺失 |
| 任务大厅 | 任务可见性、匹配规则、接单申请队列 | 部分已有 |
| 我的订单 | 进度、交付、返修、争议、超时 | 部分已有 |
| 账号资源 | 资源审核、案例审核、资源可见性 | 缺失 |
| 收益中心 | 结算状态、待结算、线下付款记录 | 部分已有 |
| 消息 | 平台通知模板、消息触达、已读状态 | 缺失 |
| 入驻资料 | 资料审核、驳回原因、历史版本 | 部分已有 |

### 2.2 主要短板

| 短板 | 影响 | 优先级 |
|---|---|---|
| 平台端单文件过大 | 后续维护困难，页面状态互相牵连，难以扩展 | P0 |
| 无发布账号运营页 | 自动发布失败、授权过期、账号风险无法集中处理 | P0 |
| 无内容库/发布记录监管页 | 平台看不到内容批次、稿件审核、发布状态闭环 | P0 |
| 无排名监控监管页 | 发布端排名监控已成主功能，但平台无周期任务和异常视角 | P1 |
| 接单方资源审核缺失 | 接单端账号资源、案例和报价无法成为可信匹配依据 | P0 |
| 接单方履约评分缺失 | 平台无法按超时、返修、争议、完成率做派单决策 | P1 |
| 消息/通知运营缺失 | 平台无法追踪关键通知是否触达接单方或商家 | P1 |
| 筛选维度不足 | 订单、Agent、资金、审计不能按品牌、平台、状态、时间精细定位 | P0 |
| 运营动作权限不完整 | 部分敏感动作仍未统一走 `platformFetch` 和权限校验 | P0 |
| 自动化证据不完整 | 本地自动化只有单个 evidenceUrl，缺少多截图、链接、平台提示 | P1 |

## 3. 建议目标信息架构

平台端建议拆为 8 个一级模块，覆盖发布端与接单端全部关键链路。

| 一级模块 | 二级能力 | 对应前台链路 |
|---|---|---|
| 运营工作台 | 待办、风险订单、失败任务、资金提醒、快捷处理 | 发布端/接单端全局 |
| 商家与品牌 | 商家列表、品牌档案、企业认证、禁用启用、品牌资产概览 | 发布端品牌管理 |
| Agent 与自动化 | Agent 任务、Skill 运行、本地自动化、人工接管、发布账号异常 | 发布端运行日志、发布账号 |
| 内容与发布 | 内容批次、内容项、发布计划、发布记录、发布失败归因 | 发布端内容库、自有账号发布 |
| 订单履约 | 任务订单、接单申请、派单/改派、交付审查、返修、争议、结算 | 发布端订单交付、接单端我的订单 |
| 网站订单 | 网站需求、AI 预览、技术订单、设计师指派、交付验收 | 发布端创建网站、接单端网站订单 |
| 接单方管理 | 入驻审核、资源审核、报价规则、履约评分、收益状态、通知记录 | 接单端全链路 |
| 资金配置审计 | 入账审核、预算/冻结、AI 算力、系统配置、权限、审计日志 | 账户余额、平台治理 |

## 4. 重点功能补齐方案

### 4.1 发布账号运营中心（P0）

目标：平台能够统一查看商家发布账号的授权状态、登录风险和自动发布失败原因。

功能：

1. 账号列表：品牌、平台、账号名、授权状态、风险状态、过期时间、最近检测时间。
2. 授权异常队列：未授权、授权过期、登录失败、权限不足。
3. 自动发布关联：展示最近 `PublishRecord`、`AgentTask`、`LocalAutomationRun`。
4. 人工处理：标记需商家重新授权、需人工发布、可重试。
5. 审计：账号状态人工修正、重试、通知商家均写入 `AuditLog`。

数据对象：

`AdAccount`、`AdAccountAuthSession`、`AdAccountUsageLog`、`PublishRecord`、`AgentTask`、`LocalAutomationRun`。

建议接口：

| 接口 | 说明 |
|---|---|
| `GET /api/platform/ad-accounts` | 账号资产列表 |
| `GET /api/platform/ad-accounts/:id` | 账号详情和关联日志 |
| `POST /api/platform/ad-accounts/:id/check` | 触发授权检测 |
| `POST /api/platform/ad-accounts/:id/notify-reauth` | 通知商家重新授权 |

### 4.2 内容与发布监管（P0）

目标：补齐发布端“内容库、自有账号发布、发布记录”的平台侧监管。

功能：

1. 内容批次列表：品牌、平台、来源任务、文章数、状态、创建时间。
2. 内容项详情：标题、平台、版本、状态、正文摘要、风险标记。
3. 发布计划监管：计划状态、目标账号、执行次数、下次执行时间。
4. 发布记录：平台、账号、状态、发布链接、错误码、人工处理分类。
5. 发布失败处理：重试、转人工、通知商家重新授权。

数据对象：

`ContentBatch`、`ContentItem`、`PublishPlan`、`PublishRecord`、`AgentTask`、`AdAccount`。

建议接口：

| 接口 | 说明 |
|---|---|
| `GET /api/platform/content-batches` | 内容批次 |
| `GET /api/platform/content-items/:id` | 内容详情 |
| `GET /api/platform/publish-plans` | 发布计划 |
| `GET /api/platform/publish-records` | 发布记录 |
| `POST /api/platform/publish-records/:id/manual-flag` | 发布记录人工标记 |

### 4.3 排名监控运营页（P1）

目标：平台能监管发布端排名监控是否按计划执行、是否出现异常。

功能：

1. 查询计划列表：品牌、关键词数、平台数、周期、下次执行时间、状态。
2. 结果异常：连续未命中、任务失败、计划过期、无结果。
3. 计划操作：暂停、恢复、立即执行、修改周期。
4. 关联 Agent：查看计划触发的 `AgentTask` 和执行日志。

数据对象：

`IndexQueryPlan`、`IndexResult`、`AgentTask`。

### 4.4 接单方资源与履约治理（P0/P1）

目标：接单端新增的账号资源、案例、报价、收益中心，需要平台侧形成可信审核和派单依据。

功能：

1. 资源审核：案例链接、平台账号、附件、公开/仅平台可见标记。
2. 报价规则审核：任务类型、预算区间、备注。
3. 履约评分：完成率、准时率、返修率、争议率、平均验收时长。
4. 收益监管：待平台确认、待线下结算、已结算。
5. 通知记录：平台派单、返修、争议、结算通知的触达和已读状态。

数据对象：

`ProviderAsset`、`ProviderPricingRule`、`TaskOrder`、`OrderDelivery`、`OrderRevision`、`SettlementRecord`、`ProviderNotification`。

建议新增字段：

| 对象 | 字段 | 说明 |
|---|---|---|
| `ProviderAsset` | `reviewStatus`、`reviewNote`、`visibility` | 资源审核和可见性 |
| `ProviderPricingRule` | `reviewStatus` | 报价规则是否可用于匹配 |
| `Provider` | `score`、`riskLevel` | 履约评分缓存 |

### 4.5 运营工作台升级（P0）

目标：从“数字看板”升级为可操作的异常处置中心。

补齐待办：

| 待办 | 来源 |
|---|---|
| 入驻待审核 | `Provider.applicationStatus=submitted` |
| 企业认证待审核 | `Organization.certStatus=pending` |
| Agent 失败/需人工处理 | `AgentTask.status=failed`、`needsReview=true` |
| 发布账号需重新授权 | `AdAccount.authStatus`、`AdAccountAuthSession.status` |
| 发布失败待处理 | `PublishRecord.status=failed` |
| 订单待派单 | `TaskOrder.status=published` 且无接单方 |
| 交付待验收 | `TaskOrder.status=pending_review` |
| 返修/争议 | `TaskOrder.status=revision/disputed` |
| 网站需求待确认 | `WebsiteRequest.status` |
| 入账待审核 | `BudgetDepositRequest.status=pending` |
| 冻结异常 | `BudgetAccount.frozen > balance` 或负数流水 |

要求：

1. 每个待办点击进入对应模块并带筛选条件。
2. 待办分 P0/P1/P2。
3. 首屏优先展示影响履约和资金的 P0。

### 4.6 权限与审计统一（P0）

目标：所有平台敏感操作都要有角色权限、二次确认和审计日志。

敏感操作：

1. 商家/品牌禁用启用。
2. 企业认证通过/驳回。
3. 接单方通过/驳回/暂停。
4. 订单派单、改派、状态修正、争议结案。
5. 网站订单指派、完成、返修。
6. 预算入账、人工调整、AI 算力调整。
7. 系统配置、Skill 路由、模型配置。
8. Agent 重试、取消、标记人工处理。
9. 发布账号人工修正、通知重新授权。

要求：

1. 前端统一使用 `platformFetch(role, ...)`。
2. 后端统一使用 `requirePlatformPermission`。
3. 操作必须填写原因时，前后端都校验。
4. `AuditLog` 记录 operator、entity、entityId、before/after 摘要、source。

## 5. 迭代拆分

### Iteration 1：平台端结构重组与 P0 入口补齐

目标：让平台端从单文件后台变成可持续扩展的运营中台。

范围：

1. 拆分 `PlatformApp.tsx`：layout、nav、dashboard、agents、orders、providers、funds、configs、audit。
2. 新增平台路由状态：支持 URL 上的 `platformView`、筛选参数、详情 ID。
3. 运营工作台待办补齐：发布失败、授权异常、待派单、企业认证、网站需求。
4. 所有现有敏感按钮统一权限调用和二次确认。

验收：

1. 平台端所有原有功能可用。
2. 点击待办能进入对应模块并带筛选。
3. 页面刷新后能保留当前平台模块和详情对象。

### Iteration 2：内容、发布账号、自动发布治理

目标：平台能看住发布端新改造后的内容生成、自有账号发布和自动化失败。

范围：

1. 发布账号运营中心。
2. 内容批次/内容项监管。
3. 发布计划/发布记录监管。
4. 自动发布失败归因和人工处理队列。
5. 发布记录与 Agent/自动化证据互链。

验收：

1. 平台可查每条发布失败属于账号授权、平台限制、内容问题还是自动化异常。
2. 平台可通知商家重新授权。
3. 平台可把发布失败标记为可重试或转人工。

### Iteration 3：接单方资源审核与履约评分

目标：平台派单不只靠名称列表，而是靠资源可信度和履约表现。

范围：

1. 接单方资源审核。
2. 报价规则审核。
3. 接单方履约评分。
4. 订单派单时展示匹配度、风险和历史履约。
5. 结算状态与收益中心联动。

验收：

1. 未审核资源不进入推荐匹配。
2. 派单/改派时能看到候选接单方能力、价格区间和履约风险。
3. 接单端收益中心与平台结算状态一致。

### Iteration 4：排名监控、消息与高级筛选

目标：补齐发布端剩余运营视角，并提高日常排障效率。

范围：

1. 排名监控运营页。
2. 消息/通知记录和模板管理。
3. Agent、订单、资金、审计高级筛选。
4. 自动化证据扩展为多证据列表。

验收：

1. 平台能发现周期查询失败、连续未命中和计划异常。
2. 平台能确认关键通知是否发送和已读。
3. 运营能在 1 分钟内定位某品牌的任务、订单、资金、发布账号、审计记录。

## 6. 优先级清单

### P0 必做

1. 拆分平台端单文件，保留原功能并建立模块边界。
2. 工作台补齐授权异常、发布失败、待派单、企业认证待审。
3. 发布账号运营中心。
4. 内容批次、发布计划、发布记录监管。
5. 接单方资源审核。
6. 派单/改派候选人展示能力、价格和履约风险。
7. 敏感操作权限与审计统一。

### P1 建议紧随

1. 排名监控运营页。
2. 接单方履约评分和风险等级。
3. 消息通知记录。
4. 高级筛选与导出。
5. 自动化多证据记录。

### P2 可后置

1. 平台运营绩效报表。
2. 接单方分层运营。
3. 财务系统对接。
4. 配置灰度发布。

## 7. 关键风险

1. 现有 `PlatformApp.tsx` 状态很多，拆分时要先做无行为变化迁移，避免同时改业务逻辑。
2. 发布账号与旧 `AccountBinding`、新 `AdAccount` 存在兼容关系，平台端要以 `AdAccount` 为主，保留 legacy 关联展示。
3. 接单方资源审核需要新增字段，涉及 Prisma migration 和种子数据。
4. 内容监管涉及发布端多个对象，需先定义统一状态口径。
5. 自动发布失败归因依赖 `PublishRecord`、`AgentTask`、`LocalAutomationRun` 的关联质量，必要时要补 `businessRef` 或 `publishRecordId`。

## 8. 建议立即开始的开发顺序

1. 先拆平台端模块，不改业务逻辑。
2. 再补平台工作台 P0 待办来源。
3. 接着做发布账号运营中心和发布记录监管。
4. 然后做接单方资源审核和派单候选人增强。
5. 最后补排名监控、消息、高级筛选。
