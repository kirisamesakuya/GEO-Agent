# GEO投放助手 Demo 版研发与 AI 改造约束文档

## 1. 文档目的

本项目当前是早期 Demo / POC 版本，用于表达产品方向、三端流程、页面结构和业务样板。

研发后续可能会拉取本项目代码，并使用 AI 辅助改造到公司真实产品体系中。因此必须明确：

```text
Demo 代码可作为产品参考，不可直接等同生产实现。
```

本约束文档用于告诉研发和 AI：

1. 哪些逻辑只是 Demo 快速方案。
2. 哪些地方必须接入公司线上真实体系。
3. 哪些代码注释需要补充，避免 AI 误读。
4. 后续前端页面继续迭代时应遵守哪些边界。

## 2. 总体约束

### 2.1 Demo 只表达产品，不承担生产安全

当前 Demo 可以继续用于：

1. 展示三端产品结构。
2. 展示核心页面和交互。
3. 展示业务流程闭环。
4. 展示状态和字段含义。
5. 给研发和 AI 提供页面参考。

但不能直接作为生产依据的部分包括：

1. 用户登录。
2. 用户鉴权。
3. 角色权限。
4. 多租户数据隔离。
5. 计费扣费。
6. 结算提现。
7. 第三方账号授权。
8. 任务调度。
9. 文件存储。
10. 数据库部署。
11. 审计风控。

这些必须以公司真实线上产品体系为准。

## 3. 必须标注为 Demo 的代码类型

后续代码中遇到以下逻辑，必须增加注释。

建议统一注释格式：

```ts
/**
 * DEMO_ONLY:
 * 当前逻辑仅用于 Demo 演示，不可作为生产实现。
 *
 * PRODUCTION_TODO:
 * 真实产品中应接入 xxx 系统 / xxx 权限 / xxx 服务。
 */
```

## 4. 需要重点加注释的地方

### 4.1 三端入口切换

当前 Demo 可能使用：

```text
?app=provider
?app=platform
```

或在一个 SPA 中切换三端。

必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前通过 URL 参数切换商家端、接单端、平台端，仅用于演示。
 *
 * PRODUCTION_TODO:
 * 真实上线应由独立域名或独立前端入口决定端类型：
 * - 商家端：app.xxx.com
 * - 接单端：provider.xxx.com
 * - 平台端：admin.xxx.com
 */
```

### 4.2 平台端角色切换

当前 Demo 如果使用 localStorage 或前端选择角色，例如：

```text
geo_platform_role
X-Platform-Role
role query/body
```

必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前平台端角色由前端模拟切换，仅用于展示不同运营角色视角。
 *
 * PRODUCTION_TODO:
 * 真实产品中角色必须来自登录用户的后端权限系统。
 * 后端不得信任 localStorage、query、body 或 X-Platform-Role。
 */
```

### 4.3 接单端 providerId

当前 Demo 如果由前端传：

```text
providerId
providerName
```

必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前 providerId 由前端传入，用于快速演示接单方身份。
 *
 * PRODUCTION_TODO:
 * 真实产品中 providerId 必须由登录态解析。
 * 接单方只能访问自己绑定的 provider 数据。
 */
```

### 4.4 商家端品牌选择

当前 Demo 如果使用：

```text
localStorage selected brand
brandName query/body
```

必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前品牌通过前端选择或 localStorage 保存，仅用于演示多品牌切换。
 *
 * PRODUCTION_TODO:
 * 真实产品中品牌必须从当前登录用户所属 organization/brand 权限中读取。
 * 后端所有查询必须按 organizationId / brandId 做数据隔离。
 */
```

### 4.5 Seed 数据和演示数据

当前 Demo 有大量 seed 数据和默认演示品牌、服务商、订单。

必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前数据用于本地演示和产品样板展示。
 *
 * PRODUCTION_TODO:
 * 生产环境不得自动写入 demo 数据。
 * 生产初始化只能写入必要系统配置。
 */
```

### 4.6 计费、余额、AI 点数

当前 Demo 中的余额、AI Credits、充值、扣费如果是模拟逻辑，必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前余额、充值、AI 点数仅用于展示页面和流程。
 *
 * PRODUCTION_TODO:
 * 真实产品中必须接入公司统一计费、订单、支付、退款和对账系统。
 */
```

### 4.7 结算和提现

当前 Demo 的服务商收益、提现、结算状态如果是简化逻辑，必须注释：

```ts
/**
 * DEMO_ONLY:
 * 当前结算和提现为演示流程，不代表真实财务规则。
 *
 * PRODUCTION_TODO:
 * 真实产品中应接入财务结算、提现审核、发票、税务、风控和打款系统。
 */
```

### 4.8 文件上传

当前如果使用本地 `uploads/`：

```ts
/**
 * DEMO_ONLY:
 * 当前文件上传到本地 uploads 目录，仅用于演示。
 *
 * PRODUCTION_TODO:
 * 真实产品中应接入 OSS/S3/云存储，并增加鉴权、大小限制、病毒扫描、访问控制。
 */
```

### 4.9 Agent / Hermes / AI 执行逻辑

当前如果存在 mock、轮询、直接调用模型等快速方案：

```ts
/**
 * DEMO_ONLY:
 * 当前 Agent 执行逻辑用于演示任务流转。
 *
 * PRODUCTION_TODO:
 * 真实产品中应接入任务队列、执行器、重试、超时、幂等、审计和人工确认机制。
 */
```

### 4.10 平台配置

当前如果平台配置可直接在前端或接口中修改：

```ts
/**
 * DEMO_ONLY:
 * 当前系统配置修改用于演示平台运营能力。
 *
 * PRODUCTION_TODO:
 * 真实产品中高风险配置必须走权限校验、审批流、版本记录和回滚机制。
 */
```

## 5. 后续前端迭代约束

前端页面和功能点可以继续迭代，但必须遵守：

1. 页面可以表达未来真实功能。
2. 不要为了 Demo 引入伪安全逻辑。
3. 涉及权限、计费、结算的地方要标注生产替换点。
4. 不要把平台端模拟角色包装成真实权限。
5. 不要把前端传入的 `providerId`、`brandName` 设计成正式方案。
6. 不要把 Demo seed 当作真实业务数据结构。
7. 每个新增模块都要说明当前 Demo 行为、真实业务规则、生产替换点。

## 6. 给 AI 的统一提示

建议在项目 README 或开发交接文档中加入：

```md
本项目是早期 Demo 版。
AI 在阅读和改造代码时，请注意：

1. 页面结构和用户流程可以参考。
2. Demo 数据、localStorage 角色、前端传 providerId、前端传 role 不可作为生产实现。
3. 真实用户、权限、计费、结算、租户隔离必须接入公司线上系统。
4. 涉及安全和资金的逻辑，应以正式后端服务为准。
5. 不要直接把 Demo 的快速实现复制到生产代码。
```

## 7. 验收要求

后续每次产品 Demo 迭代完成后，除了页面可用，还要检查：

1. 是否新增了 Demo-only 逻辑。
2. 是否对 Demo-only 逻辑加了注释。
3. 是否说明了生产替换方式。
4. 是否影响三端边界。
5. 是否会让 AI 误以为这是生产逻辑。
6. 是否更新了对应产品/改造文档。
